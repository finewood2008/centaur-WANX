# 示例助手

`npm run seed-demo` 会把这里的助手装进本机（`~/.local/share/wanxiang/apps`）。
Codespace 创建时自动跑过一次，所以打开就能看到。已经装过的不会被覆盖。

## demo-meeting-todo · 待办整理助手

**这不是手写的样板，是真跑出来的。** `scripts/make-demo.ts` 驱动了一场真实的产品经理
访谈——每轮从它给的选项里挑，聊满 9 个槽位，再 finalize 组装，然后放进一份会议记录、
按了一次「让它跑一次」。

所以下面这些都是真的：

| 文件 | 是什么 |
|---|---|
| `prd.md` | 11 节双语需求文档，那场对话的投影 |
| `rationale.yml` | 判断沉淀——每个槽位「为什么这么选」，加上产品经理归纳的三节 |
| `skills/…/SKILL.md` | 从 `workflow` / `boundaries` / `params` 确定性编译出来的工作手册 |
| `workspace/8月28日项目周会.md` | 一份合成的会议记录，当作「资料」 |
| `runs/…/output.md` | 助手照着手册跑一遍交回的待办清单（28.9 秒） |

### 值得对照着看的地方

访谈里定下的边界，在交付物里是**看得见地被执行了**的：

| 访谈定的 | 交付物里的表现 |
|---|---|
| 不对未提及负责人的待办做推测，一律归入待确认组 | 末尾真的有一个「待确认组」 |
| 不做紧急程度排序或优先级标注 | 它按**负责人**分组，而不是按紧急度排 |
| 不主动追问缺失信息，只标注 | 「越快越好」被标成「非具体日期，视为缺失截止时间」而不是去猜一个 |

**访谈 → PRD → SKILL.md → 实际行为** 这条链是通的，这也是整个产品要证明的事。

会议记录里的人名和事都是编的。

### 关于工作流程只有一步

`app.yml` 里 `workflow.steps` 只有一条，但那一条内部写着「第一步…第二步…」。

原因是产品的一个现存限制：`runFinalize` 会用**用户在访谈里的选择**覆盖定义器生成的
`workflow.steps`（「用户的选择是权威的」），而访谈那一问用户通常只勾一个选项。
定义器本来会产出 3–6 步。这个取舍目前偏向了「不改写用户」，代价是手册可能偏粗。

## 想自己造一个

```sh
npm start
# 打开 http://127.0.0.1:8788，点「＋ 造一个助手」
```

或者复现这个示例的造法：

```sh
npm start                                        # 一个终端
npx tsx scripts/make-demo.ts "你的一句话意图"      # 另一个终端
```
