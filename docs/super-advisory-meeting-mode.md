# 超级参谋团：围绕用户的多人会议模式

日期：2026-10-02。版本：会议模式 v0.2。

本稿依据用户实际试用反馈重新定义会议体验。用户进一步以“皇帝听大臣商议、必要时发言、最终裁决”明确节奏：主持人自动组织，用户掌握目标、边界及裁决权，无需逐段点选。已实现会前沟通、议程确认、自动派工、判断卡、文字反馈和明确裁决；模型发言的质量与节奏仍需实际使用检验。与旧方案冲突时，以本稿的会议节奏与用户互动规则为准。

## 1. 产品中心

参谋团为当前用户的具体问题服务。用户是会议的委托人、议题主人和最终决策者；主持人兼会议秘书，负责理解意图、组织讨论、提炼信息和持续与用户沟通；参谋提供不同角度的专业意见。

用户应持续知道：我们现在在帮我解决什么、为什么讨论这个、哪些观点与我的处境有关、现在是否需要我判断、我刚才的意见怎样改变了会议。

“皇帝与大臣”是议题权和裁决权的体验比喻。界面保留专业、平等的称呼；核心是让用户居于会议中心、可以安心旁听。参谋需要有理有据地提出异议，主持人不能为取悦用户压下不同观点。主持人兼任会议秘书，复用 WANX 原生 Teams 与专家 Agent。

会议可以质疑用户的假设，必须说明依据和代价。尊重体现为准确理解、允许纠正、提供可比较的选择，以及让用户的意见实际影响议程；不靠恭维、角色扮演或重复称呼营造。

## 2. 会前沟通：先了解意图，再请参谋

输入话题后进入主持人与用户的一小段沟通，此时不向参谋派工。

主持人先用一两句话说明对问题的理解，再提出一个最影响讨论方向的问题。例如用户说“讨论半人马AI学院的市场运营策略”，主持人可以问：

> 我先确认一下，你这次最想让参谋团帮你看清哪件事？是学院该怎样定位、近期怎样吸引合适的学员，还是怎样减轻你亲自投入的负担？也可以直接说你最困扰的地方。

对应选项卡：确认学院定位 / 找近期运营突破口 / 减轻我的投入。用户始终可以打字表达不同目标；选项不穷尽答案，也不能预先替用户决定学院必须增长或独立盈利。

会前通常进行两三次简短交流，但不强制凑轮次。每次只问一个关键问题，根据上一条回答决定是否追问约束或已有尝试。明确的原始要求可以少问；信息不足时，用户可选择“按现有信息开始”，主持人须标明尚未确认的前提。

知君资料用于减少重复询问。主持人可以说“资料里提到你能投入的时间比较有限，这次仍然是主要约束吗？”；不能把历史偏好当作本场目标，也不能通过罗列私密细节表现自己很了解用户。无相关资料时正常沟通。

## 3. 开会前的议题简报

沟通后，主持人给用户一张简短的会议简报：

- **今天帮你看清什么**：本次需要解决的问题和预期产出。
- **围绕你的哪些条件**：本场已确认的资源、约束与偏好；未确认的假设单独注明。
- **先讨论哪件事**：第一项议程及它为什么值得先谈。
- **请谁参与**：首先邀请的参谋，以及各自要回答什么。

用户通过“就按这个开始”“调整讨论重点”，或文字补充确认简报。开会动作本身即可完成确认，不再追加一次重复确认。

简报示例（条件需要经用户确认）：

> 这次先帮你判断学院接下来一个月应优先做什么。以你每周能投入的时间为约束，产出一项能落地的小实验。先请战略参谋和质疑参谋比较学院的三种定位；确定主次后，再请实践参谋拆行动。

## 4. 一段会议如何推进

基本节奏是：**用户定题与边界 → 主持人组织参谋讨论、交锋和深入 → 秘书阶段呈报 → 必要时请用户判断 → 主持人据此继续 → 呈交最终方案供用户裁决。**

一段讨论围绕一个具体问题。一次只请一位参谋，围绕一个具体观点讲清理由；需要时请其他参谋补充、反驳或检验。无需所有参谋每段都发言。主时间线展示观点、依据和对用户的影响，长讨论在独立区域滚动，输入和判断卡始终可操作。

主持人在用户确认的目标与边界内，可以自动推进多段研讨：调度成员、等待结果、指出分歧、要求反驳、深入分支和整理。每段可以给用户一份简短呈报，然后继续；呈报本身不要求回应。

只有三类节点正式请用户发言：缺少会改变结论的个人事实；需要修改原定目标、突破边界或作价值取舍；已有可比较的方案，需要最终裁决。用户未回应时不得默认替他选择，安静等待并保留已形成的内容。存在大量新想法不等于可以自动换题。

用户随时可以插话、纠正事实、缩小范围、要求更具体或结束会议。插话优先于预定议程；主持人先回应这条意见，再说明后续怎样调整。正在讨论时也不能禁用用户输入。

## 5. 秘书整理：从发言变成用户可判断的信息

主持人阶段呈报优先提炼一个最重要的观点或分歧，并按当前需要说明：

1. 各方最值得用户关注的观点，真正的分歧在哪里。
2. 这些观点怎样影响用户自己的目标、时间、资源或选择。
3. 主持人的建议及理由，尚缺的事实或尚未验证的假设。
4. 接下来准备怎样深入；确需用户参与时，说明当前只需判断的一件事。

示例：

> 两位参谋的分歧是先扩大招生，还是先筛选适合共创的人。对你来说，关键差别在于：前者需要持续的内容和承接投入，后者更看重少量学员带来的真实问题。按你刚才确认的时间约束，我建议先检验共创路线；但这取决于学院的首要目标。你更希望下一步深入哪条？

这不是替用户拍板。主持人可以有建议，用户可以不采纳，且不采纳后会议应沿新的方向继续。

## 6. 决策卡与文字是同一条交互通路

仅在需要用户判断或最终裁决时显示一张决策卡，放在输入区附近。普通阶段呈报可以自动继续，不弹卡、不要求点击。默认使用嵌入式卡片，避免模态弹窗挡住讨论或打断阅读；细节比较可以由用户主动展开。

每张卡只问一个问题，提供两三个来自本段真实讨论的选项。每个选项包含“选择什么”和一句实际取舍；有推荐时说明推荐依据。不生成装饰性按钮，也不默认提交任何选项。

| 选项示例 | 告诉用户的取舍 |
| --- | --- |
| 先验证共创路线 | 更贴合低投入约束，短期招生规模可能较小 |
| 先验证招生转化 | 能较快检验需求，但需要明确承接能力 |
| 再比较两条路线 | 请参谋补充成本和最小实验，再做判断 |

用户也可以直接输入“我两条都不想走，先聊现有学员为什么没留下来”。文字和点选都记录为用户的意见，并立即替换旧卡、改变后续议程。主持人需回应，例如：“收到，你现在更关心已有学员的持续参与。我先收起招生问题，下一段围绕留存展开。”

卡片不能停留在旧阶段。一次选择只生效一次；旧卡、旧成员回报或重连不得再次触发已结束的议程。

无需用户判断时，主持人自动继续，用户保留暂停与调整重点的入口。需要判断时，卡片可提供“先按现有条件继续研究”或“再议”，但这不能视为接受主持人推荐，也不能突破原有边界。

## 7. 参谋发言怎样体现“为我服务”

参谋收到的是主持人组织的具体任务：用户当前目标、已经确认的约束、用户最近的判断、与本次任务相关的资料，以及本次需要回答的问题。

每个观点要回答三个问题：建议是什么；为什么适合或不适合这个用户；需要验证什么。不能以通用行业分析、长篇理论或对资料的自由联想代替回答。

例如用户已明确“本月不追求扩大招生”，后续不再把新增招生作为默认目标。参谋若认为这个限制有问题，可以提出挑战及依据，交由主持人整理给用户判断。

未获用户确认的事实不得固化为前提。引用知君资料时标明来源与时效；主界面只呈现与当前判断相关的摘要，完整来源仍可查看。

## 8. 界面围绕当前用户任务组织

保留已有的会议列表、讨论区和成果区，不另建复杂工作台。

- **顶部**：本次目标、当前议程、当前状态；用户能随时调整重点或暂停。
- **中间**：主持人开场、参谋依次发言、秘书整理；发言逐条完整显示。讨论区独立滚动。
- **底部固定区**：始终可用的文字输入，提醒用户“你可以旁听，也可以随时调整重点”；需要判断时才出现决策卡。在等待参谋期间显示正在处理哪个问题。
- **右侧**：用户已经确认的目标与条件、关键观点、分歧、用户已做的选择、下一步；知君参考资料另设标签。

进展以“当前正在帮你判断什么”和已形成的结论体现，不用主持推进次数作为主进度指标。没有采纳的参谋建议不能展示为用户决策，暂存想法与已决定行动必须分清。

## 9. 收尾形成一份给用户的会议简报

用户结束或请求阶段整理时，主持人交付：本次围绕什么问题、用户作了哪些决定及理由、哪些分歧仍未解决、建议先做哪件事，以及可以下次继续的议题。

会议进入最终裁决时，主持人呈交两三个可比较的方案：各自适合用户的理由、代价、主要异议和验证办法，以及主持人的推荐与依据。用户可选择采纳、修改后采纳、要求再议，或用文字裁决。事实不足时可暂不决定。

没有决定也可收尾，如实记为仍在比较；不能为形成成果自动替用户选方案。任务分配、保存为知君事实或向外发送，需要各自已有的用户授权，会议总结本身不构成授权。

最终采纳或结束会议时，生成并保存一份会议报告，包含用户裁决、目标和约束、核心观点、实际分歧、建议行动、待确认问题、用户已做的判断、参会名单和资料来源。建议行动中的负责人和时间属于待确认建议，不自动变成任务。缺失内容如实注明；已结束的旧会议可按留存内容补生成报告。

报告在会议内预览，可以切回原讨论记录，并通过 WANX SDK 导出可编辑的 Word 文档。导出复用 WANX 的文档转换模块和原会议存储。结束后的报告固定保存，迟到的参谋回报不能改写用户裁决或已形成的报告。

## 10. 复用现有 WANX 模块的实施边界

继续复用现有账号、私有主持人与用户选择的专家 Agent、Teams 派工与 inbox、原生线程历史、知君上下文读取，以及 WANX SDK 的会话接口。

需要改变的是参谋团应用自己的会议状态与调度策略：

- 在同一原生会议线程里加入会前沟通和用户确认阶段。
- 为当前议程保存目标、已确认约束、阶段简报和一张有效决策卡。
- 点选选项和输入文字使用同一用户反馈流程；保存选择及它造成的议程变化。
- 成员回报按所属议程收集，由主持人归纳和推动交锋；在确认范围内自动深入，不能每个回报都自动开启新议题。
- 区分普通阶段呈报、等待关键用户意见和最终待裁决：前者可继续，后两者才等待用户；没有真正待判断的问题不生成卡片。
- 用服务端状态限制派工与阶段转换，不能只靠修改主持人提示词。
- 暂停、用户插话、改目标和断线重连时，防止旧结果唤醒旧议程或重复输出旧摘要。

API 层保持请求校验与适配；业务规则放在现有 infra 服务内。客户端通过 SDK 展示状态及提交反馈，不自行组织模型或直接写个人资料。新增接口或字段需要同步 SDK 合同；不另建账户、聊天存储或模型平台。

## 11. 可验证的体验要求

1. 普通新会议在用户确认前不派工，会前每次只呈现一个问题；明确要求直接开会时沿用用户已给出的目标和条件。
2. 第一段讨论至少引用一项用户已表达的目标或条件；无资料时不得编造个人背景。
3. 用户选择不同选项或输入不同意见，后续派工和秘书简报确实改变，不只是多显示一条聊天记录。
4. 用户会前确认后不再操作，主持人仍能在原定范围内完成多段研讨、交锋和呈报；普通呈报不强制用户回应。
5. 只在关键个人事实、目标或边界改变、价值取舍及最终裁决时等待用户；等待期间不持续发言或自行跳到新话题。
6. 用户在参谋发言时可以输入；修改目标后旧回报保存但不再驱动旧议程，暂停不被回叫突破。
7. 相同回报、重复点选和重连不重复派工、重复摘要或重新显示过期卡片。
8. 长内容及最小窗口下，当前决策卡与输入区仍可操作，用户阅读历史时不被强制滚到底部。
9. 会议简报区分用户决定、参谋建议和未验证假设，并保留尚未解决的分歧。最终方案得到用户裁决前不能标为已采纳。

完成代码修改后执行相关功能测试、客户端真实窗口测试和仓库规定的 `make all`。真实效果还应观察：用户能否说清这场会议正在帮自己解决什么，能否指出自己的哪次意见改变了下一步，以及会议后是否得到有用的判断或行动。


## 专家与短轮讨论补充（2026-10-02）

模型在 WANX 配置，参谋团只读取。设置管理常用专家，开会选择本场成员；复用 WANX ExpertCatalog 和 SkillHub 模板安装，不固定四位参谋。本场名单是调度边界，旧会议成员与历史保留。

每次只讨论一个问题。参谋针对其他参谋的具体观点补充、质疑、修正；主持人指出最重要的观点或分歧并邀请下一位。除用户需要裁决或阶段整理外，不输出面面俱到的综合报告。历史发言完整展示，用户随时插话，后续围绕最新反馈继续。

## 口语与逐个发言补充（2026-10-02）

每位参谋先提出一个明确建议或担心，再解释原因，并给一个与用户条件有关的例子、代价或验证办法。像当面说话一样，使用日常口语，必要的专业词随即解释；不以抽象术语或口号代替具体观点。不设固定字数上限，不为缩短而省略重要理由，删除无关背景和重复。

主持人一次只向一位参谋派工，收到这位的结果后再请下一位回应。客户端将新发言按顺序逐步呈现；即使多条结果一次到达，或轮询先读到完整历史，也不能同时展开多位发言。用户可点击「显示本条全文」快读，期间始终可以插话。裁决选项等前面的发言呈现完再出现，避免阅读过程中跳到下一个决定。旧记录和报告直接完整显示；长发言不截断，历史与实时结果不重复。系统要求减少动态效果时不使用逐字动画。

## 独立可读的会议摘要与资料出处（2026-10-02）

右侧复用 report_draft 的 overview、key_points、disagreements、actions 与 open_questions，先展示目前最重要的判断，再呈现核心观点。每个观点卡将具体建议与理由、依据和对用户的影响分开；分歧、风险、建议行动、用户意见与最终裁决、待确认事项各自成区。派工和等待回报的研究放在折叠区，不算核心观点；本场目标与条件可以展开查阅。用户无需阅读全文对话，也能理解当前判断及还需验证什么。旧会议没有报告草稿时沿用已保存的简报与观点，不生成新事实。

知君资料默认直接显示实际内容，内容下方可展开出处与性质。记忆通过原生 Memory 对象取得断言、原始事件或资料页正文；可验证原始对话归属时显示对话主题。知识库按现有原生检索标记归属到实际文件与片段，不将一个文件的内容归给另一个文件，也不为没有返回的片段编造正文。用户原话、原文引用、AI 回复、AI 推测与已确认资料继续区分。编号仅用于 SDK 引用排除与去重，界面和模型上下文采用可读标题；来源排除仍生效。
