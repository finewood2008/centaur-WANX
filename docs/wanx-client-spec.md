# wanx-client 实施规格

状态：第一阶段 seam 实现已落地；真实平台字段、设备身份材料和盒端部署参数仍通过外部 adapter 注入，基于 [`wanx-project-structure-plan.md`](wanx-project-structure-plan.md)。

本规格定义统一用户桌面端 `wanx-client/` 的第一阶段交付边界。它把盒端访问、平台设备管理、首次接入、原生 Dashboard 和定制专家 UI 之间的接口写成可追踪的契约；实现以 Node 原生 ESM seam 和可注入 adapter 落在 `wanx-client/`。

## 1. 目标与非目标

### 1.1 目标

- 用户登录平台账号后，可以从设备目录选择有权限的盒子。
- 客户端可以完成首次发现、认领、配网、初始化，并保存稳定的 `device_id` 与当前可访问地址。
- 客户端通过盒子 IP 直接访问盒端 Octop 的 HTTPS、WebSocket、SSE/流式接口。
- 用户可以打开与盒端版本一致的原生 Dashboard，也可以进入内置的定制专家 UI。
- 多盒子切换、地址变化、会话失效和授权撤销不会串用旧盒子的上下文或凭据。
- Octop 的 Dashboard、公开 API、认证、业务权限和流式协议保持原样。

### 1.2 非目标

- 不新增连接 SDK、HTTP 代理、逐接口代理清单或盒端应用网关。
- 不实现组网协议；后续组网只提供可路由 IP 和网络安全边界。
- 不迁移或复用 `wanx-desktop/`、`wanx-admin-desktop/` 的完整运行时、网关或 SDK 宿主。
- 不在 `src/octop/` 中加入平台设备表、配网逻辑、平台账号逻辑或客户端专用 API。
- 不复制 Dashboard 页面，不为任意专家动态生成 UI，不增加专家应用商店或盒端 UI 托管服务。
- 不以关闭浏览器安全检查、放宽证书校验或把长期 token 放进 URL 来解决跨源或登录问题。

## 2. 术语和上下文

| 术语 | 定义 |
|---|---|
| 平台账号 | `wanx-client` 使用的平台用户身份、会话和设备授权来源。 |
| 盒端账号 | 目标盒子内 Octop 的本地用户、角色和业务权限。 |
| `device_id` | 平台设备目录中的稳定设备主键；地址变化不改变它。 |
| `box_id` | 客户端上下文中与 `device_id` 对应的盒子标识；不得把 Host URL 当作主键。 |
| `baseURL` | `scheme://host[:port]` 形式的盒端根地址，不含用户名、密码、路径、查询或片段。 |
| Agent ID | 盒端运行中 Agent 实例的 ID；与专家模板 ID 分离，并按盒子隔离。 |
| seam | 两个模块或一个模块与外部协议之间可替换、可观察的输入/输出边界。本规格中的测试只验证 seam 契约。 |

## 3. 组件边界和依赖

```text
account/ ───────────────► 平台公开 API、shell/ 凭据存储
provisioning/ ─────────► BLE/发现、既有初始化接口、平台认领接口
devices/ ──────────────► 平台设备目录、box-access/
octop/dashboard.ts ────► shell/ 窗口能力、当前盒端地址
expert-apps/ ──────────► octop/api/、octop/context.ts
octop/api/ ────────────► box-access/
box-access/ ───────────► 盒端公开 HTTPS / WebSocket / SSE 接口
shell/ ────────────────► 桌面运行时和操作系统
```

客户端内部按以下目录落地；只创建有实际实现的文件，不预建空模块：

```text
wanx-client/
├── shell/
├── account/
├── provisioning/
├── devices/
├── box-access/
├── octop/
├── expert-apps/
├── tests/
└── README.md
```

`box-access/` 是客户端内部的普通代码，不独立发布、不运行在盒端，也不提供代理服务器。

当前实现使用 Node 原生 ESM 的 `.mjs` 文件和可注入 adapter；规格中的 `.ts` 文件名表示职责位置，后缀不改变模块边界或 seam 契约。

## 4. 外部契约

### 4.1 平台设备目录

平台接口必须能提供：`device_id`、用户授权状态、候选地址及其来源/更新时间、盒端设备身份材料（或可验证引用）。客户端必须把地址当作可变候选，把 `device_id` 当作稳定主键。

平台账号 token 只用于平台接口。平台设备列表中的“在线”是平台上报状态，不等价于客户端当前可达；客户端必须单独呈现可达状态。

### 4.2 首次接入结果

发现、身份读取、配网和初始化接口需要能返回：设备身份、配网结果、可访问 `baseURL`（或可解析的地址）、平台认领结果，以及盒端 Octop 首次账号设置/关联状态。日常业务请求不得经过 provisioning 转发。

### 4.3 盒端入口

- 默认目标是 `<baseURL>/api/health`、原生 Dashboard 根页、已有公开 HTTP API、WebSocket 和 SSE/流式端点。
- 远程盒端使用受信任的 HTTPS；HTTP 只允许用于本机回环地址。
- 直接使用 IP 时，证书必须匹配该 IP 且被客户端信任。
- 盒端部署需在可达网卡监听（例如 `0.0.0.0` 或指定接口）并放行端口；这是部署配置，不是 Octop 业务改造。
- 定制 UI 的跨源请求只使用 Octop 现有 `cors_origins` 能力和明确的 Origin；WebSocket Origin 与认证按原生端点规则验证。

### 4.4 Octop 认证和业务权限

客户端不复制 Octop 用户表或数据库。`box-access/session.ts` 只保存目标盒子、Octop 用户和会话状态；平台身份与盒端本地身份的关联必须使用目标 Octop 版本支持的认证/SSO 机制。

平台撤权必须有盒端会话撤销或等价的可验证动作；仅隐藏客户端入口不满足撤权完成条件。普通成员不得因定制 UI 获得超出盒端账号的权限。

## 5. 行为规格

### 5.1 地址准备

1. `account/` 或 `devices/` 提供候选 `baseURL`。
2. `box-access/address.ts` 校验根地址格式、协议、主机、端口和禁止字段。
3. `box-access/health.ts` 以该地址调用 `/api/health`，把网络失败、TLS/身份失败、非就绪响应和成功分开建模。
4. 健康成功只表示服务就绪；客户端还必须完成设备身份校验和 Octop 登录，不能把健康成功当作归属或认证成功。
5. 地址更新后必须重新校验目标；旧盒子的 token 不得发送到未经确认的新地址。

人工输入可作为诊断入口；正常入口从设备目录取得地址。

### 5.2 原生 Dashboard

`devices/` 选择盒子后，客户端完成地址准备并让 `octop/dashboard.ts` 请求桌面窗口打开 `<baseURL>/`。页面、静态资源、同源 `/api`、WebSocket 和流式请求由盒端 Dashboard 自己处理。客户端不得拦截、重写或代理逐个 Dashboard 请求。

Dashboard 与定制 UI 的 token 不因同源假设自动共享。若目标版本支持统一登录，需单独验证；否则 Dashboard 走其原生登录流程。

### 5.3 定制专家 UI

1. `expert-apps/registry.ts` 按专家类型选择内置 UI；没有定制 UI 的实例回退到原生 Dashboard。
2. `octop/context.ts` 提供 `boxId`、`baseURL`、Octop 用户和目标 `agentId`。
3. 专家模板 ID 用公开接口找到或创建当前盒子、当前用户可访问的 Agent 实例，再把实例 `agentId` 放入调用上下文。
4. `octop/api/` 只组织目标 Octop 版本的公开 API 参数、返回类型和调用方法，统一经 `box-access/` 发起请求。
5. WebSocket、SSE 和流式认证遵循各自原生端点；不得假定浏览器 WebSocket 可以任意增加 Authorization 请求头。
6. 若所需能力没有公开 API，记录为能力缺口，不能由客户端读取数据库、Python 内部模块或盒端文件系统补齐。

### 5.4 会话和多盒子切换

会话键至少包含 `device_id`/`box_id` 和 Octop 用户；专家页面状态再包含 `agentId`。切换盒子、退出登录或会话失效时，客户端必须：

- 关闭旧 WebSocket；
- 取消未完成的 HTTP、SSE 和流式请求；
- 清理旧页面上下文和错误状态；
- 阻止旧响应写入新盒子或新 Agent 的界面；
- 只在目标重新验证后使用缓存会话自动重连。

不可达必须与“未初始化”分开呈现。网络恢复可触发地址健康检查和有效会话重连，不重复首次认领或配网。

### 5.5 版本和升级

客户端适配集中在 `octop/api/`。每次固定版本升级至少验证：原生认证、Dashboard/静态资源、定制 UI 所需公开 API、WebSocket/SSE/流式协议、盒端初始化接口和数据库迁移。客户端不得依赖 Octop 私有数据库结构或 Python 模块。

## 6. Seam 契约

| Seam ID | 边界 | 输入 | 可观察输出/不变量 |
|---|---|---|---|
| S-01 | `account/` ↔ 平台会话 | 登录、续期、退出、平台 token | 平台 token 生命周期独立；错误可区分；不写入 Octop 会话存储。 |
| S-02 | `provisioning/` ↔ 发现/配网/认领 | 发现请求、设备身份、网络配置 | 返回身份、`device_id`、地址和阶段结果；不承载日常业务请求。 |
| S-03 | `devices/` ↔ 平台设备目录 | 设备列表、授权、候选地址 | 稳定主键与可变地址分离；平台在线与本地可达分离。 |
| S-04 | `address.ts` ↔ 输入地址 | `baseURL` 字符串 | 接受合法根地址；拒绝 userinfo、路径、查询、片段和不允许的协议；更新后产生新验证目标。 |
| S-05 | `health.ts` ↔ `/api/health` | 已校验 `baseURL`、超时、取消信号 | 返回 ready/unreachable/tls-or-identity/not-ready 等可区分结果；不创建业务会话。 |
| S-06 | 设备身份校验 ↔ 盒端身份材料 | `device_id`、证书/身份证明、当前地址 | 目标身份匹配才可继续；地址变更不能复用未验证旧 token。 |
| S-07 | `session.ts` ↔ Octop 认证 | 盒端登录、续期、退出、失效 | token 按盒子和用户隔离；失效清理；不把平台 token 当 Octop token。 |
| S-08 | `http.ts` ↔ 盒端 HTTP API | method、路径、认证、body、取消信号 | 直接发往目标盒端；不经客户端代理；取消和错误映射可观察。 |
| S-09 | `socket.ts` ↔ WebSocket/SSE/流式端点 | endpoint、Origin/认证、会话、取消 | 按端点原生握手；切换时关闭旧连接；事件不会交叉写入新上下文。 |
| S-10 | `dashboard.ts` ↔ 桌面窗口 | 已验证 `baseURL` | 打开目标盒端根页；不拦截或重写逐个业务请求。 |
| S-11 | `octop/context.ts` ↔ expert-apps | `boxId`、`baseURL`、Octop user、`agentId` | 上下文完整且按盒子/Agent 隔离；模板 ID 不冒充 Agent ID。 |
| S-12 | `octop/api/` ↔ 公开 Octop API | 类型化参数、公开路径和响应 | 只调用公开接口；权限错误原样可区分；无数据库或 Python 内部依赖。 |
| S-13 | `registry.ts` ↔ 专家 UI | 专家模板/类型、已安装实例 | 有登记 UI 才进入定制页；无 UI 回退 Dashboard；不动态加载任意代码。 |
| S-14 | 客户端页面 ↔ CORS/Origin | 页面来源、请求/WS Origin、认证 | 只使用明确允许的来源；HTTP、WS、SSE 认证策略分别符合原生规则。 |
| S-15 | 平台撤权 ↔ 盒端会话/客户端入口 | 授权状态变更、撤销结果 | 客户端隐藏与盒端会话失效可分别观察；未完成撤销不能报告完成。 |
| S-16 | 部署配置 ↔ 盒端服务 | bind host、port、证书、网络 ACL | 目标网卡可达、证书匹配、端口开放；不改变 Octop 业务逻辑。 |
| S-17 | 固定 Octop 版本 ↔ 客户端适配 | 认证、公开 API、流式协议、初始化接口版本 | 兼容性结果按接口记录；缺口进入适配任务，不以私有实现绕过。 |

## 7. 测试策略：只测 seam

测试只验证第 6 节列出的输入、输出、错误分类、取消、隔离和请求目标。允许使用 fake transport、fake platform API、fake window、fake discovery/provisioning adapter 和协议级 fixtures；这些替身必须实现 seam 契约。

不得把以下内容作为本规格的测试目标：

- React 组件像素、截图或真实浏览器布局；
- Octop 内部函数、私有数据库、Python 模块或实现细节；
- 旧桌面端完整运行时是否能被新客户端导入；
- 通过客户端代理把业务请求“打通”的端到端测试；
- 把平台在线记录直接当作本机可达的测试；
- 以固定 IP、Unix 路径或操作系统实现细节作为通用断言。

最小 seam 测试集合如下；具体测试文件随实现放入 `wanx-client/tests/`，任务文档只要求这些 seam 被覆盖：

| 覆盖目标 | 必须验证 |
|---|---|
| 地址与健康 | 合法/非法 URL、HTTPS 规则、健康结果分类、取消和地址更新重验证。 |
| 身份与会话 | 设备身份不匹配拒绝、平台/Octop token 分离、按盒子隔离、失效清理、旧 token 不发送到新地址。 |
| 请求与流式 | HTTP 目标直连、取消、WS/SSE 原生握手、断开和事件隔离。 |
| Dashboard 与专家上下文 | 只打开目标根页、无请求代理；上下文包含正确盒子/用户/Agent；模板与实例 ID 分离。 |
| 设备与 provisioning | 认领结果、地址持久化、授权/可达状态分离、不可达不等于未初始化。 |
| 权限与兼容 | 撤权闭环、公开 API 权限错误、CORS/Origin 契约、固定版本兼容性检查。 |

## 8. 验收门槛

第一阶段可以交付，必须同时满足：

1. 设备目录能提供稳定 `device_id` 和可更新地址，首次流程能产生可验证的盒端访问入口。
2. Host URL、HTTPS/证书、设备身份和 `/api/health` 的结果彼此区分。
3. 原生 Dashboard 的页面和资源由目标盒端提供，客户端没有逐接口代理。
4. 至少一个定制专家 UI 能在正确的盒子、用户和 Agent 上下文中调用公开 API，并完成其流式结果展示。
5. 多盒子切换、地址变化、会话失效和取消不会产生跨盒子/跨 Agent 响应串写。
6. 平台 token、盒端 token 和平台授权撤销的边界可验证；普通成员权限不因 UI 变化而扩大。
7. 目标 Octop 固定版本的公开接口、Dashboard、认证和初始化接口完成兼容性记录。
8. 第 7 节的 seam 测试通过；测试不依赖私有实现或代理链路。

## 9. 待确认项

以下问题阻塞对应接口的最终实现，但不改变本规格的边界：

- 发现/配网完成后返回盒子 IP 的具体协议和字段；
- 平台设备目录的地址字段、来源、过期和多地址优先级；
- 盒端证书信任与设备身份校验材料；
- 目标 Octop 版本的认证/SSO 机制及平台到本地用户的关联方式；
- 所有者、普通成员、管理员的权限映射和撤权 API；
- 桌面技术栈的页面源、CORS/请求策略与 Dashboard 登录衔接；
- 首个定制专家 UI 对应的公开 API、Agent 创建方式和版本兼容范围。

## 10. Trace bullets

每个 trace bullet 是一个可追踪的交付单元；任务文档必须按此列表一一拆分，不跨条目合并。

- **TB-01 平台账号边界**：平台登录、续期、退出和凭据存储独立于盒端账号。
- **TB-02 首次接入闭环**：发现设备身份、配网、认领、初始化并产出可访问地址。
- **TB-03 设备目录模型**：以稳定 `device_id` 管理多盒子、授权、候选地址和本地可达状态。
- **TB-04 地址规范化**：实现 Host URL 根地址校验和诊断输入规则。
- **TB-05 健康检查**：通过 `/api/health` 区分服务就绪、不可达、TLS/身份错误和非就绪。
- **TB-06 设备身份校验**：地址变化后验证目标身份，阻止旧盒子 token 外发。
- **TB-07 Octop 会话**：实现按盒子/用户隔离的登录、续期、失效和退出。
- **TB-08 HTTP 直连传输**：上传、普通请求和错误/取消直接到盒端公开 API。
- **TB-09 WebSocket/SSE/流式传输**：按原生协议认证、关闭和隔离事件流。
- **TB-10 原生 Dashboard 入口**：打开目标盒端页面，不复制页面或代理业务请求。
- **TB-11 专家上下文**：按盒子、Octop 用户、专家模板和 Agent 实例建立上下文。
- **TB-12 公开 API 适配**：仅对公开 Octop API 提供类型化调用，记录能力缺口。
- **TB-13 专家 UI 注册**：有登记进入定制 UI，无登记回退 Dashboard，不动态加载代码。
- **TB-14 Origin/CORS 约束**：明确配置页面、HTTP、WS、SSE 的来源和认证策略。
- **TB-15 授权撤销**：同步处理客户端入口、盒端会话失效和未完成撤销状态。
- **TB-16 盒端部署可达性**：验证监听地址、端口、证书和网络 ACL，不改业务逻辑。
- **TB-17 Octop 版本兼容**：对固定版本的认证、Dashboard、公开 API、流式协议和初始化接口做升级验证。
