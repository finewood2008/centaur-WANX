# 万象应用商店交易与应用授权实施方案

日期：2026-10-14  
状态：设计方案，尚未实施。本文保存产品与技术设计，不代表相关能力已经上线。

## 1 目标与产品原则

万象应用商店采用以账号为中心的软件获取与使用模式：用户在商店领取免费应用或购买软件，平台记录其使用权益；用户选择自己有权访问的盒子后，系统自动完成应用准备、授权同步和应用会话建立。正常使用不要求客户填写盒端用户 ID、运行脚本或联系管理员逐台开通。

建议首期支持免费领取和一次性买断，再增加订阅；数据模型从一开始容纳订阅、试用和赠送。首期具体售卖方式尚待业务确认，本文不将该建议视为已确定的商业政策。

建议采用以下默认规则：

- 购买权益归万象账号所有；同一账号在 macOS、Windows 登录、重装或更换电脑后可以恢复购买。
- 在授权范围内切换本人盒子无需重复购买。设备数量和并发限制由商品条款明确规定，不能隐含在技术实现中。
- 软件使用费与模型调用费、云端算力费分别展示；购买软件不自动意味着无限模型额度。
- 购买软件不自动取得他人盒子的访问权；拥有盒子也不自动拥有所有付费软件。
- 盒子转让不转让原账号的软件权益，原账号对该盒子的授权应失效。
- 用户数据与软件权益分离；卸载、到期、退款不能默认删除用户数据。

## 2 当前问题与已有基础

此前超级参谋团在 248 上提示“此账号尚未获得应用使用权限”，直接原因是客户端已经安装应用，但盒端缺少对应产品注册、部署启用和用户访问授权。通过盒端现有管理接口补齐配置后，授权状态已确认；这一人工补齐方式适用于排障，不应成为应用商店的客户流程。

截至本方案讨论时，现有能力与缺口如下：

| 环节 | 已有基础 | 本方案需要补齐 |
| --- | --- | --- |
| 应用发行 | Admin 管理应用、版本、制品、发布指针和审计 | 商品、价格、售卖方式与权益规则 |
| 客户端安装 | 候选版本选择、签名与哈希验证、安装更新和卸载 | 根据账号权益显示购买、领取和恢复入口 |
| 账号与盒子 | Consumer 身份、盒子归属、授权同步和回执机制 | 应用级权益投影与应用激活回执 |
| 盒端应用 | Octop 产品注册、部署开关和用户访问控制 | 受信任的自动注册、启用、授权和撤销 |
| 应用会话 | Host、Bridge 与应用作用域会话 | 通用应用身份映射、逐应用能力校验 |
| 交易 | 尚未形成商店支付与权益闭环 | 订单、支付、退款、对账和权益生命周期 |

现有包签名证明制品来源及完整性，不能证明当前账号已经购买。现有盒子访问许可也不能代替软件使用权益。当前 Host 清单中的 capabilities 主要作为发行元数据，不能直接当作已经实现的应用沙箱。

## 3 权益与权限分层

实际可用条件为：**账号应用权益有效、盒子访问权有效、盒端应用已准备就绪且符合盒主策略、用户已同意所需权限**。各层分别校验并返回明确状态。

| 层次 | 决定的问题 | 权威来源 |
| --- | --- | --- |
| 应用商业权益 | 此账号是否拥有该软件，范围和有效期是什么 | Admin 权益服务 |
| 盒子访问权限 | 此账号是否可访问这台盒子 | 平台归属及成员授权 |
| 盒端部署与资源策略 | 软件是否启用，是否允许使用本盒模型、存储等资源 | 盒主策略与盒端状态 |
| 应用能力授权 | 此应用可调用哪些 API、访问哪些数据 | 签名应用身份、用户同意与服务端策略 |
| 运行会话 | 本次请求是否仍处于有效授权范围 | Host、Bridge 与 Octop |

平台可以签发购买、免费领取、试用或赠送权益。盒子管理员管理本盒资源和成员使用范围，但不能通过本地“启用”按钮生成付费软件的购买权益。运维赠送必须经平台管理入口完成，并记录来源、操作者和原因。

共享盒子场景下，软件购买与盒主批准是两个步骤。用户已经购买但盒主尚未允许部署时，应显示“已购买，等待盒主允许在此盒子使用”，不得要求再次付款。

## 4 完整用户流程

### 4.1 领取或购买

1. 用户登录万象账号，无需连接盒子即可浏览商店。
2. 应用详情显示售价、售卖方式、适用平台、盒端版本要求、模型依赖、权限及是否另计模型费用。
3. 免费应用点击“获取”，平台创建免费权益；付费应用由平台创建订单并发起支付。
4. 平台依据可信支付通知或主动查询确认支付，生成权益。客户端支付成功回跳不作为付款依据。
5. 客户端显示“已购买”并提供安装入口；此时盒子离线不影响购买结果。

### 4.2 安装并首次打开

1. 客户端校验账号权益和制品兼容性，下载并验证签名、哈希及包结构。
2. 用户选择有权访问的盒子；展示本次应用所需的数据权限和模型资源。
3. 对本人盒子，在用户确认后自动准备应用；共享盒子按盒主策略自动允许或进入审批。
4. Admin 校验权益、盒子访问权、归属版本和权限同意记录，签发面向该应用与盒子的授权。
5. Bridge 验证授权，映射已验证的账号身份到本地 SSO 用户，调用既有管理能力完成产品注册、部署启用和应用访问授权。
6. 盒端原子保存授权状态并返回真实回执。模型、版本或资源条件不满足时返回可恢复的准备状态。
7. 回执确认后建立受限的应用会话并打开应用，不要求再次输入盒端账号密码。

已付款但应用准备失败时保留购买权益，只重试准备与授权步骤。客户端不能把“支付成功”“云端已发授权”直接显示为“盒端应用可用”。

### 4.3 再次使用与恢复购买

同一账号再次打开时自动复用有效状态并在后台续期。换电脑或重装后，从“我的已购／恢复购买”恢复权益和可安装列表，不以本机文件是否存在作为所有权依据。

换账号后，即使软件包仍在本机，也必须按新账号重新校验权益。切换盒子时重新校验该盒子的归属、访问权限、部署条件和应用授权。

## 5 各工程职责

| 工程或组件 | 责任 | 边界 |
| --- | --- | --- |
| nexusaos-admin | 商品、订单、支付退款、权益、签名许可、同步任务与审计 | 是商业权益的权威来源 |
| 万象客户端与 Host | 商店、购买状态、安装、恢复购买、权限确认、选择盒子及应用会话 | 不信任本地购买标记，不持有支付密钥或盒端管理凭据 |
| wanx-bridge | 验签、账号映射、盒端授权投影、回执、撤销和会话限制 | 使用受限的管理通道，不接受客户端任意授予权限 |
| Octop | 原生产品与用户权限、应用会话及业务资源访问检查 | 保持原生启动，仅在必要授权接入点做少量改动 |
| centuarai-os 与 box.sh | 部署兼容版本、安装信任配置、运行授权同步组件及健康检查 | 部署软件不等于给所有账号购买或授权 |
| 知君与超级参谋团等应用 | 声明应用身份、能力和依赖，调用 Host 受限接口 | 不自行实现支付判定，不读取账号或管理密钥 |

继续使用原生 Octop 入口；该方案不需要恢复 `wanx_runtime` 包装启动层。交易逻辑放在 Admin，客户端交互放在万象，盒端适配优先放在 Bridge。

## 6 通用应用身份与授权协议

### 6.1 统一应用标识

将签名市场应用 ID、盒端产品 ID、能力集合及权限版本建立明确映射，例如超级参谋团的市场应用 ID 对应盒端 `super-advisory`。映射由受信任的发行与平台配置提供，不能由应用进程自行声明后获得权限。

当前针对特定应用的作用域判断应改为通用注册机制。未知应用或缺少映射必须拒绝建立业务会话，不能回退为普通 WANX 的宽泛权限。

发布新版本时，新增敏感能力需要用户重新同意；更新安装包不能自动扩大原有权限。Host 限制应用可调用的接口，服务端独立检查能力与资源范围，不能只依靠前端隐藏按钮。

### 6.2 短期应用许可

建议签名许可至少绑定以下信息，最终字段名称在接口设计阶段确定：

- 签发者、接收方、许可 ID、签名密钥 ID、签发及过期时间。
- 平台账号、客户端身份、目标盒子设备身份与归属版本。
- 市场应用 ID、盒端产品 ID、权益 ID 与权益版本。
- 能力集合、资源范围、权限同意版本与协议版本。

校验范围包括签名、接收方、时效、账号映射、盒子身份、归属版本与重放约束。发行包签名密钥与运行许可签名密钥分别管理，支持轮换。

现有 Consumer 授权快照有严格合同，不能直接向旧协议随意追加商业字段。应使用版本化扩展或独立应用许可协议，明确最低客户端、Bridge 和平台版本。

### 6.3 盒端投影与真实回执

复用现有授权更新、摘要和 ACK 的设计原则，为应用权益增加独立、可追踪的投影版本。同步必须幂等，同一任务重试不重复创建产品、用户或授权。

盒端保存授权来源，区分平台商业授权与盒主本地限制。平台同步不得覆盖盒主明确设置的拒绝策略；同一账号存在多个有效权益来源时，撤销其中一个来源不应误删其他合法权益。

注册、启用、用户访问更新使用受控管理接口或领域服务，不由客户端直写数据库。不允许伪造回执，不能用“任务已下发”代替“盒端已生效”。

## 7 交易与权益数据模型

以下为新增逻辑实体建议，具体表名在实施时按 Admin 规范确定。

| 实体 | 主要内容 |
| --- | --- |
| 商品与 SKU | 应用、售卖方式、金额和币种、有效期、适用版本、设备与并发条款 |
| 订单与订单项 | 购买账号、商品、金额与条款快照、状态、幂等标识 |
| 支付与退款流水 | 渠道订单号、通知事件唯一标识、金额、状态、对账结果 |
| 账号应用权益 | 应用、受益账号、来源、有效期、范围、权益版本、撤销原因 |
| 权限同意记录 | 账号、应用、权限版本、同意时间及相关资源范围 |
| 盒端应用投影 | 账号、盒子、应用、归属版本、目标授权版本、摘要与 ACK |
| 可靠事件与审计 | 待投递事件、重试、操作来源、人工处理与状态变更记录 |

权益来源至少区分免费领取、订单、试用、平台赠送、历史迁移和企业分配。权益不是订单中的一个简单布尔值，同一账号同一应用可能同时拥有多项合法来源。

建议将待支付、已支付、已关闭与退款流程分开表达。权益使用有效、到期、撤销等状态；盒端激活使用待准备、同步中、可用、失败及已撤销等状态。各状态之间通过明确事件关联，不混为一个“安装成功”标志。

## 8 支付确认与一致性

订单金额、商品及购买账号由服务端确定。支付通知必须按支付渠道协议验签、核对订单和金额，必要时主动查询；重复通知应返回一致结果，不能重复发放权益。

订单付款确认、权益发放和可靠待投递事件应在同一业务事务中持久化。盒端准备与授权通过后台任务执行，不在支付回调内等待盒子上线。通知重试、乱序、订单关闭后的晚到付款和退款通知都必须有处理规则及对账补偿。

退款成功后按来源撤销对应权益；若仍有其他有效权益，应继续允许相应使用范围。订阅取消自动续费不等于立即终止已付费周期，到期后再停止续发许可。

接口应支持幂等下单、查询订单、查询我的权益、免费领取、恢复购买、请求应用激活、查询激活状态及回执。具体 URL 和请求响应结构属于后续接口合同，不将这些建议冒充为现有 API。

## 9 会话续期与撤销

买断权益可以长期存在，但运行会话保持短期有效。应用会话有效期不得超过父级盒子访问租约、应用许可或权益剩余有效期中的最短者。

现有 WANX P2P 链路的盒子访问租约上限为 120 秒，应用会话应遵守父租约约束。客户端在后台提前续期并缓存有效结果，避免每次点击都串行访问平台造成启动延迟。

退款、权益撤销、盒子转让或成员移除后，平台停止续发许可，并推动盒端更新授权。HTTP 请求与长连接需要在适当边界重新检查状态，关闭或限制已撤销会话，不能只在打开应用时检查一次。

首期建议在线使用并容忍短时网络抖动。长期离线使用需要独立的离线许可政策：可离线时长、适用功能、设备绑定和回收规则应单独设计。完全离线期间无法保证即时收到退款或撤销通知，必须明确最长生效延迟。

## 10 产品界面与错误状态

| 状态 | 用户看到的内容 | 操作 |
| --- | --- | --- |
| 未拥有付费应用 | 价格、购买方式及适用条件 | 购买 |
| 未领取免费应用 | 免费 | 获取 |
| 已拥有但未安装 | 已购买或已获取 | 安装 |
| 已安装且条件齐备 | 可用 | 打开 |
| 已购买但盒子离线 | 已购买，等待盒子连接 | 选择其他盒子或稍后重试 |
| 盒端应用准备中 | 正在准备应用及授权 | 自动等待，可查看进度 |
| 共享盒子未批准 | 等待盒主允许在此盒子使用 | 申请使用或选择其他盒子 |
| 盒端版本过低 | 需要更新盒端 | 更新指引 |
| 模型或资源缺失 | 缺少所需模型或资源 | 配置资源或选择其他盒子 |
| 权益到期 | 使用期限已结束 | 续费或查看订单 |
| 权限范围扩大 | 新版本需要新增权限 | 查看并确认 |
| 盒主明确拒绝 | 此盒子未允许该应用 | 联系盒主或选择其他盒子 |

“我的已购”提供恢复购买和订单入口；“设置 → 盒子 → 应用与成员”提供资源启用与成员审批入口。普通客户不填写 WANX 用户 ID，由系统映射平台账号和盒端用户。

当前对多种 401／403 统一显示“联系管理员”的行为需要拆分。错误应区分未购买、盒子无访问权、等待授权同步、未启用、版本不兼容和许可失效，并提供对应下一步。

商品下架还应区分停止新销售与撤销既有使用权。正常停止销售不应自动撤销已购权益；已有用户能否继续下载和获得更新，按购买时条款处理。

## 11 迁移与兼容

- 现有明确人工授权可以迁移为有来源、有审计的历史赠送权益；不能将所有已安装用户或所有盒子管理员自动视为购买用户。
- 迁移必须识别已有盒主拒绝策略，不能以自动授权覆盖。
- 知君现有兼容放行规则应制定迁移窗口，最终纳入统一权益模型，避免长期形成商业权限绕过。
- 协议不兼容时显示升级要求，不能降级为无作用域会话。
- 授权功能灰度上线，按账号和盒子检查投影结果；失败支持重试与回滚，不删除用户数据。
- 首期只开放第一方或经过审核的应用。当前 Electron 应用运行方式不等于完整第三方沙箱；开放第三方之前需完善进程、文件、网络和凭据隔离。

## 12 实施阶段与依赖

### 阶段一 免费权益与自动开通

建立统一应用身份、免费领取权益、权限同意、盒端激活与真实回执；完善 Host 和服务端的应用能力校验、错误分类与撤销链路。以超级参谋团作为完整验证样例。

依赖：账号到盒端 SSO 用户映射、可信应用注册、可用的盒子访问授权和兼容版本部署。

验收：新账号领取应用后，在本人盒子上一键安装打开，全程无需手工授予本地用户权限；缺少盒子权限或用户撤销后不能继续调用业务接口。

### 阶段二 买断支付闭环

增加商品价格、订单、支付、我的已购、恢复购买、退款、对账和权益撤销。复用阶段一的激活链路。

依赖：业务确认买断适用版本、设备并发限制、支付渠道、退款及升级条款。

验收：付款与软件准备解耦；重复通知不重复发权益；换电脑可恢复，退款后停止续发授权，准备失败不会重复收费。

### 阶段三 订阅与组织授权

支持试用、按月按年订阅、续费、赠送与兑换码，以及组织购买和席位分配。企业授权需要明确权益受益者是组织还是个人，以及人员离职后的回收规则。

### 阶段四 第三方生态

补齐开发者入驻、审核、应用隔离、漏洞处置、发行者密钥管理和结算分账。完成隔离与权限验收后再开放第三方可执行应用。

## 13 涉及工程与验证清单

后续实施应先分别制定 Admin、客户端、Bridge 和 Octop 的接口合同及兼容策略，再进行代码修改。

| 工程 | 重点模块 |
| --- | --- |
| nexusaos-admin | 应用市场服务、Consumer 授权、商品订单权益服务、管理界面及数据库迁移 |
| centuarai-wanx | wanx-client/applications、app-host、octop/gateway、商店与设置页面 |
| centuarai-wanx | wanx-bridge 授权同步、原生应用会话交换及 infra/applications 权限接入 |
| centuarai-os | 盒端组件发布、信任配置、兼容性和健康检查 |
| 应用工程 | 签名清单、能力声明、版本要求与 Host 接入 |

至少验证以下场景：

1. 购买成功且盒子在线，自动激活并打开。
2. 购买成功但盒子离线，权益保留，上线后完成激活。
3. 用户已买软件但没有目标盒子权限，访问被拒绝。
4. 用户是盒主但未购买付费软件，不能通过本地启用绕过购买。
5. 同一安装包切换账号，按新账号权益重新校验。
6. 同账号切换 macOS 与 Windows、重装或更换电脑，正确恢复购买。
7. 同账号切换两台有权访问的盒子，分别建立有效授权。
8. 支付通知重复、乱序、丢失及晚到，通过幂等处理和对账恢复一致状态。
9. 授权同步中断后重试，不重复建用户或产生虚假 ACK。
10. 退款、订阅到期、成员移除与盒子转让后，旧会话按规定时限失效。
11. 多来源权益撤销其中一项，仍保留其他有效权益。
12. 应用新增权限时要求再次同意，未知应用不能获取宽泛会话。
13. 盒主明确拒绝不被平台自动同步覆盖，退款和卸载不删除用户数据。

## 14 待业务确认

1. 首期只做免费和买断，还是同时上线订阅。
2. 买断包含哪些软件版本与后续升级，是否限制设备或并发数量。
3. 是否允许在共享盒子上使用个人购买的软件，以及是否默认需要盒主批准。
4. 软件是否提供试用，模型费用如何呈现和计量。
5. 支付渠道、退款条款，以及是否需要长期离线许可。

这些决策影响商品配置与许可范围，不影响先建设账号权益、自动激活、应用隔离和可追踪授权回执这一基础链路。
