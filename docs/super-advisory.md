# 半人马AI-个人议事厅：产品与实施方案

日期：2026-10-02。版本：初始实施方案 v0.1，附会议模式 v0.2、专家与讨论修订 v0.3。

用户试用后要求会议围绕本人展开，先由主持人沟通和确认议题，再通过阶段提炼、决策卡及文字互动推进。新的体验与调度依据见 [围绕用户的多人会议模式 v0.2](super-advisory-meeting-mode.md)。下文保留初始方案与实施记录；其中拿到话题就派工、连续跨议题推进的节奏已由 v0.2 调整。

本文记录已经确认的产品方向，以及基于当前工作树和 WANX SDK 的实施建议。产品方向已确认；本文没有表示功能已实现、模型效果已验证或真实盒子已联调。

## 1. 已确认的产品方向

- 暂定名称：**半人马AI-个人议事厅**。
- 形态：独立应用，与知君一样通过 WANX SDK 使用平台账号及功能模块。
- 身份：使用与知君相同的 WANX 账号体系，不建立第二套用户账号。
- 核心体验：多个不同模型、不同角度的 Agent，在主持人引导下持续发现、连接和深入探索有价值的想法。
- 主持人：自主推进讨论；发现新线索后继续追问、调动成员、调整探索方向，在需要用户判断时等待回应。
- 知君上下文：默认按话题自动检索本人的相关数据，展示参考来源，并允许用户调整本场材料。
- 推进方式：不要求用户逐轮点击继续；阶段性整理后可以继续探索，不以固定复核轮次定义产品。

## 2. 首版体验建议

用户登录并进入一个话题后，主持人理解议题，检索相关知君背景，邀请合适的参谋展开讨论。用户可以随时插话、指定方向、调整材料、暂停或要求阶段整理。

首版建议提供主持人及一组可调整的默认参谋：

| 角色 | 主要贡献 |
| --- | --- |
| 主持人 | 理解用户、发现线索、安排下一步探索、连接不同观点、整理阶段成果 |
| 创意参谋 | 提出新方向、组合已有想法、寻找跨领域联系 |
| 策略参谋 | 结合用户目标和背景，判断哪些方向值得继续深入 |
| 实践参谋 | 把想法转成具体场景、实验或行动路径 |
| 挑战参谋 | 提出反例、隐藏假设和遗漏，帮助产生更好的替代方案 |

角色数量属于首版建议。模型从 WANX 读取，由 WANX 管理服务与部署绑定；用户在参谋团内选择专家，并可从 WANX 已启用的对话模型中指定每位专家使用的模型。参与者不足或模型不可用时，如实说明，不能由一个模型冒充多位成员。

首版界面建议围绕三个内容区域：话题列表、讨论时间线、当前探索方向与阶段成果。发言显示专家名称及实际讨论内容；来源面板显示本场使用的知君材料。用户看到的是讨论及成果，运行细节仅在有助于理解状态时展示。

## 3. 主持人如何持续推进

主持人的下一步应由当前讨论内容决定。可选择的动作包括：请成员展开、请另一位成员补充、连接两个想法、提出反例、补检索背景、转向新分支、询问用户、整理阶段成果。

每次调度都应说明本次要探索的新问题，避免让所有成员重复回答原始议题。不同成员的结果可以触发新的探索，但同一结果不得重复触发相同派工。

主持人需要持续掌握：

- 当前议题与用户目标。
- 已经讨论过的方向，以及尚未展开的分支。
- 新想法及其来源、依据和待验证假设。
- 当前值得深入的问题、参与成员和在途任务。
- 用户最新的补充与方向调整。

遇到重复时，先改变角度或问题；需要用户取舍时，整理可选方向并等待回应。阶段整理应保留不同方案与未解决问题，不强迫形成一致意见。

“自主推进”需要服务端执行状态支撑。运行、等待用户、暂停和结束是场次状态，不能通过某段自然语言或主持人的一次 `done` 帧来推断整场已经结束。

暂停的建议语义是：立即停止后续自动派工；已在途成员结果可以保存，但不能再次唤醒自动讨论。是否支持强制取消所有在途成员，应以现有调用链的实际取消能力为准，不能把关闭窗口或关闭流当作任务已取消。

## 4. 使用知君上下文

首版实施基线是两款应用连接同一 WANX 实例，使用相同 `user_id` 识别本人。多盒子数据聚合尚未纳入首版范围。

| 数据 | 用途 |
| --- | --- |
| 用户确认的背景、目标、偏好 | 理解议题及用户实际处境 |
| 相关记忆和经历 | 找到机会、联系、经验与约束 |
| 用户上传的资料 | 提供议题事实、引用和材料 |
| 相关历史对话 | 接续先前思考，减少重复说明 |

服务端基于当前议题检索本人知君上下文，返回相关摘要或片段及来源信息。派工只携带该成员本次任务需要的内容；主持人发现新的问题时可补检索。每个引用至少保留来源类型、源标识和内容版本或时间，区分用户陈述、系统推断和讨论中新提出的设想。

用户可以查看本场参考来源、排除材料或关闭本场知君上下文。排除后停止后续引用；已经生成的历史发言如何保留应在界面明确体现，不能宣称既有发言中的内容已经自动撤回。

知君数据继续由原生记忆、知识库和历史模块保存。参谋团只保存自己的讨论、运行状态和成果引用，不建立第二套个人记忆系统。讨论设想不会自动写成知君已确认的事实；回存知君由用户明确选择，首版可以先提供成果整理与导出。

跨应用读取要由 WANX 领域服务处理：验证当前用户、来源所属用户、目标应用能力和访问范围，然后调用原有模块。客户端继续使用自己的应用会话，不持有另一款应用的登录凭据，不通过管理员接口读取个人资料。

## 5. 复用方案与当前缺口

| 层次 | 直接复用 | 需要补齐 |
| --- | --- | --- |
| 账号与产品登记 | WANX 登录、产品定义、部署、用户开通、应用会话 | 参谋团产品定义与相应应用能力 |
| Agent 与模型 | Agent 注册、模型配置、运行与工作区 | 应用内多 Agent，以及稳定的个人入口绑定 |
| 团队协作 | Teams、异步派工、成员独立 checkpoint、回叫 | 按应用选择头脑风暴主持策略及场次推进控制 |
| 讨论展示 | Chat WebSocket、说话人标识、历史投影 | 独立产品界面、探索分支与成果视图 |
| 知君背景 | 原生记忆、知识库、历史 | 同一用户跨应用上下文读取入口 |
| 客户端接入 | `centaurai-wanx 0.1.0-alpha.3` | 对新增通用接口同步 SDK 合同与实现 |

已核验的具体限制：

1. 当前 `agents_product_owner` 唯一索引限制非 WANX 应用每个用户只有一个 Agent；应用 profile 也是查询这个唯一实例。需要将“个人应用入口”与“应用内 Agent 数量”解耦，并保留知君既有 profile 的唯一性和身份。
2. 应用能力目录目前只有 chat、memory、knowledge、upload、voice；独立应用会话没有 Teams 管理或多 Agent 创建权限。SDK 接口存在不等于应用已获授权。
3. 团队创建还需要显式继承应用归属。成员和主持人应属于同一应用域；现有团队成员校验和 peer 调用已检查应用归属。
4. 原生团队主持模板强调协调与最多三句收尾，运行时也会追加主持提示。头脑风暴策略需要覆盖模板、运行时提示和回叫语义，不能只修改客户端发送的一段提示词。
5. 主持人当前工具范围包含成员调度、记忆检索和时间等。知君上下文补检索需要通过受限只读工具或领域服务注入，不能因此开放所有工作区及管理能力。
6. 现有成员派工会包含房间历史，这与接续式头脑风暴相容；若以后加入盲评或独立首轮，再单独增加上下文隔离。
7. 在途任务追踪目前在进程内，重启后丢失。保存场次状态不等于在途任务已具备持久恢复；首版应在重启后显示中断状态，核对已保存成果后再继续，避免重复派工。

这些扩展应落在原有应用、Agent、Teams 和上下文服务中。API 只负责请求校验与错误映射，客户端只通过 SDK 操作；不另建模型调用平台、聊天数据库或任务队列。

个人入口绑定采用哪个持久化位置、场次状态如何利用原有工作区或存储，属于实施时根据现有数据结构确定的技术细节。本稿不提前宣称某个未实现接口已经可用。

## 6. 实施顺序与验证

| 步骤 | 交付 | 验证依据 |
| --- | --- | --- |
| 1. 平台应用支持 | 多 Agent 与个人入口解耦、团队应用归属、授权能力 | 同一用户重复初始化幂等；不同用户及应用隔离；知君原 profile 保持可用；SQLite/PostgreSQL 合同一致 |
| 2. 本人上下文读取 | 按话题检索知君记忆、材料及历史，保留来源 | 正确命中相关内容；排除材料生效；无数据可正常讨论；跨用户读取失败；普通应用隔离继续成立 |
| 3. 主持策略与推进 | 内容驱动的调度、阶段成果、暂停及用户插话 | 连续产生不同探索任务；重复回叫不重复派工；暂停后不再自动推进；用户补充影响下一步；故障状态真实 |
| 4. SDK 与独立客户端 | 原生接口绑定、登录、话题、流式发言、来源与成果 | SDK 合同和安装检查；界面通过实际 SDK 与本机服务通信；成员身份正确；重连补历史不重复展示 |
| 5. 效果验证 | 小规模真实多模型头脑风暴评估 | 按议题评估新想法、与用户背景的关联、主持追问及可用成果；不能用消息数或单次演示证明答案更好 |

平台代码交付遵循仓库 `make all`；涉及界面时增加 TypeScript 检查与前端构建，涉及 i18n 时检查键一致性，涉及 API 时查看 `/api/docs`。真实模型效果、真实账号盒子连接和桌面安装应分别记录验收证据。

当前 SDK 的新产品远程连接身份仍需要平台支持。独立应用可先使用 SDK 已有的可信 HTTPS 或本机回环接入验证功能；不能把现有 `omnia-desktop` 身份直接当作新产品身份，也不能把本机验证当作跨网络盒子验收。

## 9. 专家与讨论修订 v0.3（2026-10-02）

「参谋团设置」包含「专家库」和「技能市场」。模型服务、密钥与资源绑定统一在 WANX 配置，应用没有服务商写入接口，保留移除 `model_settings` 能力的边界。当前修订允许通过 brainstorm profile 的 `expert_models` 为专家指定 WANX 已启用的对话模型；不接受 host_model/member_models 等旧的位置式配置。

八类预设作为普通 WANX 专家模板进入原有 ExpertCatalog：创意、战略、实践、质疑、产品、用户研究、组织、商业。用户选择 2–12 位常用专家，发起会议时从中选择本次成员。会议保存自己的名单；更换默认专家后，旧成员保留原生 Agent 与历史供旧会议继续。

市场通过原生 `/api/experts/hub` 读取；`/api/brainstorm/experts/{slug}/import` 是薄适配，复用 SkillHub 原有模板安装、包校验、目录与 Agent workspace seeding。没有新增专家数据库或客户端技能安装器。SDK alpha.6 同步专家选择、会议名单与导入合同，JavaScript 及 Go 原生 HTTP 均可使用。

讨论按一个具体问题交替推进。参谋每次约80–180字、最多两小段，回应前一位的论点并给出补充、质疑或一个小实验；主持人短句点出分歧、邀请下一位。服务端最多两位同时发言，只允许当前会议名单派工。参谋不能另开隐蔽分会。发言逐条展示，输入区持续可用，用户插话使旧任务回叫失效；主持人接续最新判断。普通轮次不要求最终结论，阶段成果与用户采纳继续区分。

短发言长度属于提示策略，真实模型遵守程度和讨论质量仍需实际试用评估。脚本回归只证明协议、交替回叫、历史及用户参与流程。

## 10. 参谋模型选择 v0.4（2026-10-02）

每位已选专家的卡片提供模型下拉框，列表直接来自 WANX 当前启用、有凭据且可用于对话的模型。专家 ID 与模型引用通过 SDK alpha.8 的 `configureProfile` 保存为原生 Agent 的 `default_model`，保留身份及历史。未提交的模型赋值保留原配置，新专家未赋值时继承主持人的 WANX 模型。

服务端在任何 Agent 写入前验证完整请求：模型或服务商停用、模型不存在、仅支持 embedding、专家未被选中均拒绝。现有的讨论运行及在途任务锁继续适用；保存后后续派工使用新模型，旧会议名单与历史快照保留。主持人模型仍由 WANX 应用部署绑定配置。
