## 产品操作准则

- 用户以“打开应用”或“更新”为入口，不手工选择组件和升级顺序。同一计划不重复确认；新增收费、权限或影响需明确同意。
- 默认显示客户端产品版本、当前盒子实际套件版本及状态；构建摘要和模块明细放入详情。离线或无法核验时，不报告“已是最新版”。
- 正式发行审批绑定不可变内容。设备升级另核验操作权限，不逐盒重复审批同一发行。
- 单设备恢复验证通过后开放受控手动批量。批次汇总独立设备结果，不承诺整批原子成功。
- 下载中断可继续原任务；结果待确认先补查；基线改变须重算。不得把所有异常都映射成重新安装。

## 核心验收用例

1. 同一正式版本不能替换制品，未批准发行不出现在客户候选中，创建人不能批准自己的正式推广。
2. 候选符合平台、架构、客户端和盒端合同；未知依赖、未知版本和受限平台给出明确原因。
3. 普通成员可以查看授权范围内版本，但不能越权更新共享设备；设备接口只接受绑定身份的设备认证。
4. 下载中断、重复创建任务和重复事件不产生重复安装，任务目标不跟随渠道变化。
5. 设备切换前重新核验基线、归属和许可；篡改签名、过期许可、撤回发行均拒绝新激活。
6. 容器停止、替换和启动之间中断后，可根据持久记录恢复一致状态；恢复成功必须经过实际核验。
7. 客户端退出不取消已接受的设备任务；回执迟到不覆盖新的状态，发送命令不等于安装成功。
8. 日常 OTA 不调用首次配网、授权重建、模型重建、设备重置或旧应用清理。
9. 设置页展示实际客户端与盒端版本；切换账号或设备不复用旧授权和旧确认。
10. 批量预览区分可执行、离线等待和受阻设备，已成功设备不因批次重试重复执行。

## 首期本地交付时的边界（后续现场进展见文末）

1. 日常盒端 OTA 与完整 `box.sh deploy` 分离，只更新已纳管的万象、Semantica 业务容器。初始执行矩阵为 Ubuntu 24.04 x64；后续家庭试点显式增加 Ubuntu 26.04 x64，要求签名发行与设备平台精确匹配，未知系统仍拒绝执行。26.04 的业务兼容验收尚未完成。
2. 整盒版本只有在六个组件均有一致的真实运行证据时才显示；业务子集升级成功只更新对应组件。没有安装升级器的盒子显示尚未接入或无法核验。
3. 新应用兼容合同可以检查客户端、后端接口与专家依赖。现有 Octop 公开接口不能证明专家模板版本，也不能用父应用会话证明所有独立产品的权益；这类新合同保持阻止，并明确说明缺少的证据。没有实现绕过权限、自动迁移个人专家或改写 Octop 内部数据。旧 schema1 应用继续按原合同运行。
4. 不包含操作系统、内核、基础网络、P2P、Docker 引擎、升级器自升级和不可逆数据迁移。这些属于整体方案后续阶段。
5. 初次本地验证未提交、推送、执行生产迁移或连接设备安装更新。后续已按用户授权连接线上 Admin 和家庭盒，部署范围与信任配置见文末。正式客户端系统签名及安装验证仍未完成。

## 发布与试点顺序

1. 先部署 Admin 的新表、权限与接口，配置独立发行验签根和设备任务许可签名；保留旧 OTA 表和记录。
2. 构建包含版本中心和生产公钥的万象过渡安装包，先人工安装一次。旧客户端本身没有新升级入口，不能凭服务端更新自动获得该入口。
3. 在受支持的试点盒上进行一次受控升级器 bootstrap，核验身份、库存与健康探针。引导命令成功不等同于该盒已完成 OTA 验收。
4. 从不可变构建生成带正式产品版本的签名候选，在 Admin 登记、由另一名有权人员推广；先完成一台盒与两个正式客户端版本间的实测，再执行受控批量。
5. 试点必须验证断网、进程终止/重启、许可响应丢失、恢复核验及真实业务数据向后兼容；本地 fake Docker 和模拟 updater 测试不能替代真机安装测试。

### 已复现问题与修复

| 范围 | 原问题与影响 | 修复与证据 |
| --- | --- | --- |
| 发行身份 | 改 releaseId 后，同一产品、平台、正式版本可以替换构建或制品 | 新增不可变发行身份表，登记与推广都校验；同一内容跨渠道仍允许，真实 MySQL 并发冲突验证 |
| Admin 权限 | 设备转移租户，或管理员被禁用、删掉、撤销角色/权限后，旧计划仍可能获得执行许可 | 计划保存已授权范围，执行前锁定读取当前账号、角色、权限及设备租户；覆盖七类撤权与旧事务快照 |
| 取消证明 | 已签发切换许可后，仅报 cancelled 就能释放设备锁 | 取消必须提供原基线及服务可用证据；缺少或漂移的证据保持互斥 |
| 任务响应丢失 | 初次 claim 已提交但响应丢失，取消后盒端因没有本地事务而永久卡住 | 允许校验固定任务后确认未开始执行的取消；跨仓库 ASGI/SQL 与真实 updater 联测通过 |
| 双模块恢复 | JSON 保存后键排序改变，恢复顺序可能与实际升级顺序不符 | 严格按固定 plan.steps 的逆序恢复，双模块依赖故障注入通过 |
| 容器配置 | 与旧镜像默认值相同的显式环境配置被丢弃，新镜像默认值可能改变数据目录或模型模式 | 保留现场完整环境配置；生产 Docker 请求构造验证 HOME、MODEL_LOCAL_ONLY 保持原值 |
| 后续 CLI 部署 | OTA 账本遮蔽新 fleet 部署，合法新容器被持续标为漂移 | fleet 成功/unchanged 回执记录实际 Config、HostConfig、Mounts 摘要，OTA 只接受一致新证据；HostConfig 漂移仍阻止 |
| 幂等与并发 | execute-only 批次重放变成 403；MySQL 死锁暴露为 500 | 重放使用原 execute 权限；1205/1213 回滚后返回 409 CONCURRENT_MODIFICATION，数据库唯一约束继续兜底 |
| 库存时间 | MySQL DATETIME 秒级舍入使新的毫秒级报告误报过时 | 根据保留的原始 RFC3339 时间比较；真实 MySQL 的 .600→.700 接受、.650 拒绝 |
| Windows 安装 | 实际 electron-updater 在 PowerShell 不可用时可能跳过默认签名检查 | 独立系统验签，下载/缓存/安装前均要求明确成功；真实 NsisUpdater 配合故障注入验证失败拒绝 |
| 正式构建来源 | 未提交源码可以打成正式包并标为干净 Git 提交 | macOS/Windows 构建前后检查源码及 HEAD；发行签名纳入 sourceCommits，本地脏包不得签为正式发行 |
| 固定客户端目标 | 下载后渠道推广新版本，原已下载且仍有效的目标被误判改变 | 安装前以固定 releaseId 重新校验，继续核验撤回、过期、平台与安全代次 |
| 客户端恢复提示 | 正常账号恢复会清空本机更新恢复/成功状态 | 本机安装结果独立保留，启动旧副本不能误报更新成功 |
| 市场兼容 | 已是最新/本地更高版本提前返回，不检查新选盒子 | 同样核验签名及当前盒子能力，查询兼容历史；需要降版时给出受控恢复提示，不静默降级 |
